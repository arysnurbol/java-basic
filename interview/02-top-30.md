# Java Core

## 1. Контракт equals() и hashCode()

**Жауап.** Егер `a.equals(b)` true болса, онда `a.hashCode() == b.hashCode()` **міндетті** түрде орындалуы тиіс.
Кері бағыт міндетті емес: хеші бірдей екі объект тең болмауы мүмкін, бұл коллизия деп аталады.
Хешке негізделген коллекциялар (`HashMap`, `HashSet`) алдымен `hashCode` арқылы бакетті табады,
тек содан кейін бакет ішінде `equals` арқылы салыстырады. `equals` үшін бес талап бар:
рефлексивтілік, симметриялық, транзитивтілік, консистенттілік және `x.equals(null) == false`.

```java
class NoHash {                       // equals бар, ал hashCode ЖОҚ
    int id;
    public boolean equals(Object o) { return o instanceof NoHash k && k.id == id; }
}
Set<NoHash> set = new HashSet<>();
set.add(new NoHash(1));
set.contains(new NoHash(1));          // → false  (екі объект әртүрлі бакетке түсті)
```

⚠ **Кілт өзгеріп кетсе не болады?**
```java
Key k = new Key(1); map.put(k, "v");
k.id = 2;                             // hashCode өзгерді
map.get(k);                           // → null, бірақ size=1: жазба map ішінде «жоғалып» кетті
```
Сондықтан кілт ретінде **immutable** объектілерді қолданған дұрыс (`String`, `Integer`, `record`).

## 2. Разница между == и equals(). Что такое String pool?

**Жауап.** `==` сілтемелерді салыстырады, яғни екеуі **бір объект** па соны тексереді.
`equals` мазмұнды салыстырады, бірақ тек сол класта ол переопределён болса ғана.
**String pool** — heap-тегі арнайы аймақ. Литералдар сол жерде бір данадан сақталады,
сондықтан бірдей литералдар бір объектіге сілтейді.

```java
String a = "java", b = "java", c = new String("java");
a == b;            // → true   (екеуі де pool-дағы бір объект)
a == c;            // → false  (new әрқашан жаңа объект жасайды)
a.equals(c);       // → true
a == c.intern();   // → true   (intern() pool-дағы нұсқаны қайтарады)
```

⚠ `new String("java")` қанша объект жасайды? **1 немесе 2.** Pool-да литерал әлі жоқ болса,
литерал үшін бір объект және heap-те `new` үшін тағы бір объект құрылады.

## 3. String, StringBuilder, StringBuffer — разница

| | Өзгермелілік | Потокобезопасность | Жылдамдық |
|---|---|---|---|
| `String` | immutable | иә (immutable болғандықтан) | — |
| `StringBuilder` | mutable | жоқ | ең жылдам |
| `StringBuffer` | mutable | иә (`synchronized`) | баяуырақ, ескірген |

```java
String s = "";
for (int i = 0; i < 10_000; i++) s += i;     // әр итерацияда ЖАҢА String құрылады, O(n²)

StringBuilder sb = new StringBuilder();
for (int i = 0; i < 10_000; i++) sb.append(i); // бір буфер жеткілікті, O(n)
```

⚠ **Неге String immutable?** Үш себеп бар: string pool (бір объектіні көп жер бөліседі),
хешті кэштеуге болады (HashMap кілті ретінде ыңғайлы), қауіпсіздік және потокобезопасность.

## 4. Как создать immutable класс?

**Жауап.** 1) класс `final`; 2) барлық өрістер `private final`; 3) setter жоқ;
4) mutable өрістер конструкторда да, getter-де де **қорғаныс көшірмесі** (defensive copy) арқылы өтеді.

```java
public final class Person {
    private final String name;
    private final List<String> phones;
    public Person(String name, List<String> phones) {
        this.name = name;
        this.phones = List.copyOf(phones);     // сырттан келген тізімді көшіреміз
    }
    public List<String> getPhones() { return phones; }   // List.copyOf өзгермейтін тізім береді
}
// Java 16+: record Person(String name, List<String> phones) — өрістер final болады,
// бірақ ішкі тізімді бәрібір copyOf арқылы көшіру керек!
```

⚠ **Пайдасы:** потокобезопасность үшін синхронизация керек емес, HashMap-тың сенімді кілті бола алады,
кэштеуге болады.

## 5. Какие проблемы несёт autoboxing?

**Жауап.** 1) **Integer cache**: `==` −128…127 аралығында ғана «дұрыс» жұмыс істейді;
2) `null`-ды unboxing жасағанда **NPE** шығады; 3) циклдерде артық объектілер құрылады.

```java
Integer a = 127, b = 127, c = 128, d = 128;
a == b;          // → true   (кэштен алынған бір объект)
c == d;          // → false  (екі түрлі объект!)
c.equals(d);     // → true   ← wrapper-лерді әрқашан equals арқылы салыстыр

Integer n = null;
int z = n;       // → NullPointerException (unboxing)

Long sum = 0L;
for (long i = 0; i < 1_000_000; i++) sum += i;   // миллион Long объектісі құрылады
```

## 6. В Java передача по значению или по ссылке?

**Жауап.** **Әрқашан мән бойынша беріледі (by value).** Объект болса, **сілтеменің көшірмесі** беріледі.
Сондықтан әдіс объектінің ішін өзгерте алады, бірақ сыртқы айнымалыны басқа объектіге бағыттай алмайды.

```java
static void change(StringBuilder sb, int x) {
    sb.append("!");                  // объектінің ішін өзгертеміз: сыртқа көрінеді
    x = 99;                          // көшірмені өзгертеміз: сыртқа көрінбейді
    sb = new StringBuilder("new");   // тек локал көшірмені қайта бағыттаймыз: сыртқа көрінбейді
}
StringBuilder sb = new StringBuilder("hi"); int v = 1;
change(sb, v);
// → sb = "hi!", v = 1
```

## 7. Иерархия исключений. Checked vs Unchecked

```
Throwable
├── Error                      ← JVM ақаулары, ұстамайды: OutOfMemoryError, StackOverflowError
└── Exception                  ← checked: IOException, SQLException (өңдеу немесе throws жазу міндетті)
    └── RuntimeException       ← unchecked: NPE, IllegalArgumentException, IndexOutOfBounds…
```

**Жауап.** **Checked** түрін компилятор тексереді: оны `catch` арқылы ұстау немесе `throws` деп жариялау керек.
Бұлар сыртқы, қалпына келтіруге болатын жағдайлар (файл табылмады, желі үзілді).
**Unchecked** түрі бағдарламашының қатесін білдіреді, компилятор оны талап етпейді.

⚠ **Неге заманауи фреймворктер (Spring, Hibernate) тек unchecked қолданады?**
Checked exception `throws` арқылы барлық қабаттарға тарап, API-ды ластайды және лямбдаларға сыймайды.
Kotlin мен Scala тілдерінде checked exception мүлде жоқ.

## 8. try-with-resources и особенности finally

**Жауап.** `AutoCloseable`-ді жүзеге асыратын ресурс блоктан шыққанда **автоматты түрде жабылады**.
Бірнеше ресурс болса, олар ашылған ретіне **кері** ретпен жабылады. `close()` өзі exception лақтырса,
ол жоғалмайды: `suppressed` ретінде негізгі exception-ға тіркеледі (`e.getSuppressed()`).

```java
try (var in = new FileInputStream("a.txt");
     var out = new FileOutputStream("b.txt")) {
    in.transferTo(out);
}   // алдымен out, сосын in жабылады: finally жазудың қажеті жоқ
```

⚠ **finally және return бойынша тұзақтар:**
```java
static int f() { try { return 1; } finally { return 2; } }        // → 2 (finally жеңеді, мұны ешқашан жазба)
static int g() { int x = 1; try { return x; } finally { x = 2; } } // → 1 (return мәні алдын ала есептеліп қойылған)
```
`finally` блогы **орындалмайтын** жағдайлар: `System.exit()`, JVM құлауы, `kill -9`.

## 9. Абстрактный класс vs интерфейс

| | Абстракт класс | Интерфейс |
|---|---|---|
| Мұрагерлік | тек **біреуін** extends етуге болады | **бірнешеуін** implements етуге болады |
| Күй (state) | кез келген өріс болады | тек `public static final` константалар |
| Конструктор | бар | жоқ |
| Әдістер | кез келген | abstract, `default`, `static`, `private` (Java 9+) |
| Мағынасы | **«is-a»**: ортақ негіз және ортақ код | **«can-do»**: мінез-құлық келісімі (contract) |

```java
interface Flyable { default String fly() { return "flying"; } }
abstract class Animal { protected String name; abstract String sound(); }
class Duck extends Animal implements Flyable, Swimmable { String sound() { return "quack"; } }
```

⚠ Екі интерфейсте бірдей `default` әдіс болса, класс оны **міндетті түрде** переопределить етуі керек
(`Flyable.super.fly()` арқылы нақты нұсқасын таңдай алады).

## 10. final, finally, finalize — разница

**Жауап.**
- `final` — модификатор. Айнымалыға бір рет қана мән беріледі, әдісті переопределить етуге болмайды,
  кластан мұрагерлікке тыйым салынады.
- `finally` — `try` блогынан кейін **әрқашан** орындалатын блок.
- `finalize()` — объектіні GC жинамас бұрын шақырылатын әдіс. **Java 9-дан бастап deprecated**:
  қашан шақырылатыны белгісіз, GC-ды баяулатады, ішіндегі exception жұтылып кетеді.
  Оның орнына `try-with-resources` немесе `Cleaner` қолданылады.

```java
final List<String> list = new ArrayList<>();
list.add("ok");            // ✅ болады: final СІЛТЕМЕГЕ ғана қатысты
list = new ArrayList<>();  // ❌ компиляция қатесі
```

# Коллекциялар және Stream

## 11. Как устроен HashMap? Что такое коллизии?

**Жауап.**
- Ішінде `Node<K,V>[] table` массиві жатыр. Әр ұяшық **бакет** деп аталады.
- `put(k, v)`: `hash = h ^ (h >>> 16)` (хештің жоғарғы биттерін төменгілерімен араластырады),
  сосын индекс `(n - 1) & hash` арқылы есептеледі. Массив ұзындығы n әрқашан 2-нің дәрежесі болғандықтан,
  бұл `%` амалымен бірдей нәтиже береді, бірақ жылдамырақ.
- **Коллизия** — екі түрлі кілт бір бакетке түсетін жағдай. Ондай кілттер бакет ішінде **байланысқан тізім**
  (linked list) құрайды. Java 8-ден бастап бакеттегі элементтер саны **8-ден асса** және массив ұзындығы ≥ 64 болса,
  тізім **қызыл-қара ағашқа** айналады (treeify). Сонда ең нашар жағдайдағы күрделілік O(n)-нан O(log n)-ға түседі.
- **Resize**: `size > capacity × loadFactor` болғанда орындалады (әдепкі мәндер: 16 × 0.75 = 12).
  Массив 2 есе үлкейеді, элементтер жаңа бакеттерге қайта таратылады.
- `null` кілтке рұқсат бар, ол әрқашан 0-бакетке түседі.

```java
class BadKey { public int hashCode() { return 42; } }   // барлық кілт бір бакетке түседі
// → get() O(1) болудан қалады: алдымен O(n), treeify-дан кейін O(log n)
```

⚠ Орташа күрделілік O(1), ең нашар жағдай O(log n) (Java 8+). HashMap **потокобезопасный емес**.

## 12. ArrayList vs LinkedList

| Операция | ArrayList (массив) | LinkedList (екі жақты тізім) |
|---|---|---|
| `get(i)` | **O(1)** | O(n) |
| Соңына қосу | амортизацияланған O(1) (толғанда 1.5 есе үлкейеді) | O(1) |
| Ортасына қосу немесе жою | O(n) (элементтерді жылжыту керек) | іздеуге O(n) + байланыстарды ауыстыруға O(1) |
| Жады | ықшам, CPU кэшіне ыңғайлы | әр элемент үшін Node объектісі және 2 сілтеме |

**Жауап.** Практикада **барлық жағдайда дерлік ArrayList таңдалады**. Кезек (queue) немесе
екі жақты кезек (deque) керек болса, `ArrayDeque` қолданылады. LinkedList өте сирек тиімді болады.

## 13. Как устроен HashSet?

**Жауап.** Ішінде жай ғана **`HashMap<E, Object>`** жатыр. Элемент кілт ретінде сақталады,
ал мән ретінде бос `PRESENT` объектісі қойылады. Сондықтан HashMap-тың барлық ережелері мұнда да жарамды:
equals/hashCode контракты, O(1) күрделілік, элементтердің реті кепілдендірілмейді.

```java
Set<String> set = new HashSet<>();
set.add("a");     // іштей map.put("a", PRESENT) шақырылады
```
- `LinkedHashSet` элементтерді **қосылған ретімен** сақтайды (ішінде LinkedHashMap жатыр).
- `TreeSet` элементтерді **сұрыпталған** күйде сақтайды (ішінде TreeMap жатыр, қызыл-қара ағаш, O(log n)).

## 14. HashMap vs LinkedHashMap vs TreeMap. Comparable vs Comparator

| | Реті | get/put | null кілт |
|---|---|---|---|
| `HashMap` | кепілдендірілмейді | O(1) | болады |
| `LinkedHashMap` | қосылған реті (немесе access-order, **LRU кэшке** ыңғайлы) | O(1) | болады |
| `TreeMap` | кілт бойынша сұрыпталған | O(log n) | болмайды |

**Comparable** — объектінің «табиғи» реті, ол класстың ішінде `compareTo` арқылы анықталады.
**Comparator** — сырттан берілетін реттеу ережесі. Олардың саны кез келген бола алады.

```java
record User(String name, int age) implements Comparable<User> {
    public int compareTo(User o) { return Integer.compare(age, o.age); }   // табиғи рет: жасы бойынша
}
users.sort(Comparator.comparing(User::name).thenComparing(User::age, Comparator.reverseOrder()));
```

⚠ `compareTo` ішінде `a - b` жазба, **int overflow** болуы мүмкін. Оның орнына `Integer.compare` қолдан.

## 15. fail-fast vs fail-safe итераторы

**Жауап.** **fail-fast** итераторлары (`ArrayList`, `HashMap`) `modCount` санағышын қадағалайды.
Итерация кезінде коллекция құрылымы итератордан тыс өзгерсе, `ConcurrentModificationException` шығады.
**fail-safe** немесе weakly consistent итераторлары (`CopyOnWriteArrayList`, `ConcurrentHashMap`)
коллекцияның көшірмесімен немесе «суретімен» (snapshot) жұмыс істейді, сондықтан exception лақтырмайды.

```java
List<Integer> l = new ArrayList<>(List.of(1, 2, 3, 4));
for (Integer e : l) if (e == 2) l.remove(e);    // → ConcurrentModificationException
l.removeIf(e -> e == 2);                        // → [1, 3, 4]  ✅ дұрыс тәсіл (немесе iterator.remove())

List<Integer> cow = new CopyOnWriteArrayList<>(List.of(1, 2, 3));
for (Integer e : cow) cow.add(9);               // → [1, 2, 3, 9, 9, 9]: цикл ескі snapshot бойынша жүреді
```

## 16. Generics: стирание типов (type erasure) и PECS

**Жауап.** Generic типтері тек **компиляция кезінде** тексеріледі. Bytecode-та олар өшіріліп,
`Object` типіне немесе типтің шекарасына (bound) ауыстырылады. Нәтижесінде `new T()`, `T.class`,
`instanceof List<String>` сияқты өрнектер жұмыс істемейді.

```java
new ArrayList<String>().getClass() == new ArrayList<Integer>().getClass();   // → true
```

**PECS — Producer Extends, Consumer Super:**
```java
// src тек дерек БЕРЕДІ (producer) → extends;  dst тек дерек ҚАБЫЛДАЙДЫ (consumer) → super
static <T> void copy(List<? extends T> src, List<? super T> dst) {
    for (T t : src) dst.add(t);
}
List<? extends Number> nums = List.of(1, 2.5);
Number n = nums.get(0);   // ✅ оқуға болады
nums.add(3);              // ❌ жазуға болмайды: тізімнің нақты типі белгісіз
```

## 17. Stream API: ленивость, промежуточные и терминальные операции, map vs flatMap

**Жауап.** Stream операциялары екі түрлі болады. **Аралық** (intermediate) операциялар:
`filter`, `map`, `sorted` — олар жалқау, тек жоспар құрады. **Терминалдық** (terminal) операциялар:
`collect`, `forEach`, `findFirst` — осылар ғана өңдеуді іске қосады. Элементтер конвейерден **бір-бірлеп**
өтеді, ал `findFirst` сияқты операциялар нәтиже табылған бойда тоқтайды (short-circuit).
Бір stream-ді **бір-ақ рет** қолдануға болады.

```java
Stream<Integer> st = Stream.of(1, 2, 3).filter(n -> { System.out.println("filter " + n); return n > 1; });
// → әзірге ештеңе шықпайды
st.findFirst();
// → filter 1
// → filter 2      ← 3-элемент мүлде тексерілмейді
```
**map** әр элементті 1-ге-1 түрлендіреді. **flatMap** әр элементті stream-ге айналдырып, барлығын біріктіреді:
```java
Stream.of(List.of(1, 2), List.of(3)).flatMap(List::stream).toList();   // → [1, 2, 3]
```

⚠ `parallelStream` жұмысы ортақ `ForkJoinPool.commonPool()` арқылы орындалады. Ол I/O операцияларына
және аз деректерге тиімсіз, ал ішінде ортақ mutable күй болса, қате нәтиже береді.

# Көпағындылық (Concurrency)

## 18. Runnable vs Callable. Что такое Future?

| | `Runnable` | `Callable<V>` |
|---|---|---|
| Әдіс | `void run()` | `V call()` |
| Нәтиже | қайтармайды | қайтарады |
| Checked exception | лақтыра алмайды | лақтыра алады |

**Future** — болашақ нәтиженің «түбіртегі». `get()` нәтиже дайын болғанша **ағынды блоктайды**.
Оның басқа әдістері: `get(timeout)`, `cancel()`, `isDone()`.

```java
ExecutorService ex = Executors.newFixedThreadPool(2);
Future<Integer> f = ex.submit(() -> 6 * 7);   // Callable (нәтиже қайтарады)
f.get();                                      // → 42
ex.submit(() -> System.out.println("hi"));    // Runnable
```

## 19. Что делает volatile?

**Жауап.** `volatile` екі нәрсеге кепілдік береді: **көрінушілік** (visibility) және **орын ауыстыруға тыйым**
(reordering). Бір ағын жазған мән басқа ағындарға бірден көрінеді (кэште қалып қоймайды).
`volatile`-ге жазу мен одан кейінгі оқу арасында **happens-before** қатынасы орнайды.
Бірақ ол **атомарлыққа кепілдік бермейді**.

```java
static boolean running = true;         // volatile ЖОҚ
new Thread(() -> { while (running) n++; }).start();
Thread.sleep(500); running = false;
// → ағын 2 секундтан кейін де ТОҚТАМАДЫ (JIT мәнді тек бір рет оқитындай етіп оптимизациялады)
// volatile қосқаннан кейін → бірден тоқтады
```

⚠ **Қай жерде қолданылады:** тоқтату жалауша (stop flag), double-checked locking singleton.

## 20. Race condition. Почему volatile не подходит для счётчика? Как сделать потокобезопасный счётчик?

**Жауап.** `count++` бір операция емес, үш операция: **оқу → қосу → жазу**. Екі ағын бір мәнді
қатар оқыса, біреуінің жазған нәтижесі жоғалады. `volatile` тек көрінушілікті қамтамасыз етеді,
атомарлықты емес. Шешімдер: `synchronized`, `AtomicInteger` (CAS), `LongAdder` (қатты конкуренция кезінде).

```java
static int counter = 0;
// 2 ағынның әрқайсысы 100_000 рет counter++ жасады
// → counter = 111655  (200000 болуы керек еді!)

AtomicInteger ai = new AtomicInteger();
// сол 2 ағын ai.incrementAndGet() шақырды
// → 200000 ✅
```
**CAS (compare-and-swap)** — процессордың атомарлық инструкциясы. Логикасы: «мән әлі де `expected`-ке тең болса,
оны `new`-ге ауыстыр, әйтпесе қайтадан байқап көр».
Бұл құлыпсыз (lock-free) тәсіл, сондықтан ағын блокталмайды.

## 21. synchronized vs ReentrantLock

**Жауап.** Екеуі де **өзара жоққа шығаруды** (mutual exclusion), көрінушілікті және **реентранттылықты**
береді (құлыпты ұстап тұрған ағын оны қайта ала алады). `synchronized` қарапайым және құлып автоматты
түрде босатылады. **ReentrantLock** қосымша мүмкіндіктер береді:
- `tryLock(timeout)` — шексіз күтпеу, бұл deadlock-тың алдын алуға көмектеседі;
- `lockInterruptibly()`;
- fair (әділ) режимі;
- бірнеше `Condition`.

```java
private final Lock lock = new ReentrantLock();
void transfer() {
    lock.lock();
    try { /* критикалық секция */ }
    finally { lock.unlock(); }        // ⚠ unlock ӘРҚАШАН finally ішінде болуы тиіс
}
```
`synchronized` құлпының күйі объектінің **mark word** бөлігінде сақталады.

## 22. Что такое deadlock? Как избежать?

**Жауап.** **Deadlock** — екі немесе одан көп ағын бір-бірінің ұстап тұрған құлпын **мәңгі күтіп** қалатын жағдай.

```java
// Ағын 1: synchronized(A) { sleep; synchronized(B) {...} }
// Ағын 2: synchronized(B) { sleep; synchronized(A) {...} }
// → екі ағын да мәңгі күтеді, бағдарлама «қатып» қалады
```
**Алдын алу жолдары:**
1. Құлыптарды **әрқашан бір ретпен** алу (мысалы, id бойынша: алдымен кіші id, сосын үлкені).
2. `tryLock(timeout)` қолдану.
3. Бір уақытта ұсталатын құлыптардың санын азайту.

Deadlock-ты табу үшін `jstack <pid>` немесе `jcmd <pid> Thread.print` қолданылады.
Олардың шығысында «Found one Java-level deadlock» деген жазу шығады.

⚠ Ұқсас терминдер: **livelock** (ағындар жұмыс істеп жатады, бірақ алға жылжымайды),
**starvation** (ағынға ресурс ешқашан тимейді).

## 23. Как работает ConcurrentHashMap?

**Жауап (Java 8+).** Бүкіл map құлыпталмайды:
- **Оқу** құлыпсыз орындалады (volatile оқу).
- **Бос бакетке жазу** CAS арқылы орындалады.
- **Бос емес бакетке жазу** `synchronized` арқылы **тек сол бакеттің бірінші түйінін** құлыптайды.
- Resize бірнеше ағын арасында бөлініп орындалады.

Java 7-де map «сегменттерге» бөлінетін (lock striping), бұл тәсіл кейін бас тартылды.

```java
Map<String, Integer> chm = new ConcurrentHashMap<>();
// 4 ағынның әрқайсысы 10_000 рет орындады:
chm.merge("k", 1, Integer::sum);     // атомарлы «оқу + өзгерту + жазу»
// → 40000 ✅
chm.put(null, 1);                    // → NullPointerException
```

⚠ **null кілтке де, null мәнге де тыйым салынған.** Себебі `get()` null қайтарса, «кілт жоқ» па
әлде «мәні null» ма, көпағынды ортада оны ажырату мүмкін емес.
⚠ `if (!map.containsKey(k)) map.put(k, v)` **атомарлы емес**! Оның орнына `putIfAbsent`,
`computeIfAbsent` немесе `merge` қолдан.

## 24. Что такое пул потоков (ExecutorService) и как он работает?

**Жауап.** Пул ағындарды **қайта пайдаланады**, себебі ағын құру қымбат операция. Тапсырмалар кезекке түседі,
жұмысшы ағындар оларды кезектен алып орындайды. `ThreadPoolExecutor` параметрлері:
`corePoolSize`, `maximumPoolSize`, `keepAliveTime`, `workQueue`, `RejectedExecutionHandler`.

**Жаңа тапсырма келгенде пул қалай әрекет етеді:**
1. Ағын саны `core`-дан аз болса → **жаңа ағын** құрылады.
2. Әйтпесе → тапсырма **кезекке** қойылады.
3. Кезек толы болса және ағын саны `max`-тан аз болса → тағы жаңа ағын құрылады.
4. Ол да мүмкін болмаса → **reject** (әдепкі бойынша `RejectedExecutionException` лақтырылады).

```java
ExecutorService ex = Executors.newFixedThreadPool(4);
try { ex.submit(task); }
finally { ex.shutdown(); }   // ⚠ shutdown болмаса, JVM тоқтамайды: пулдың ағындары демон емес
```

⚠ `Executors.newFixedThreadPool` **шексіз** `LinkedBlockingQueue` қолданады, сондықтан кезек өсіп,
OOM-ға апаруы мүмкін. Продакшнда `new ThreadPoolExecutor(...)` арқылы шегі бар кезекпен құрған дұрыс.
**Пул өлшемі:** CPU-ға ауыр тапсырмалар үшін ≈ ядро саны, I/O тапсырмалары үшін одан әлдеқайда көп.

## 25. CompletableFuture

**Жауап.** Бұл **блоктамайтын** Future. Асинхрон қадамдарды тізбекке біріктіруге,
бірнеше нәтижені біріктіруге және қателерді өңдеуге мүмкіндік береді.
Әдепкі бойынша тапсырмалар `ForkJoinPool.commonPool()`-да орындалады.

```java
int r = CompletableFuture.supplyAsync(() -> 10)            // асинхрон бастау
        .thenApply(n -> n * 2)                             // нәтижені түрлендіру (map) → 20
        .thenCombine(CompletableFuture.supplyAsync(() -> 5), Integer::sum)   // екі нәтижені біріктіру → 25
        .exceptionally(e -> -1)                            // қате болса, әдепкі мән қайтарады
        .join();
// → 25
```
- `thenApply` = map, `thenCompose` = flatMap (келесі қадам өзі CF қайтарғанда).
- `allOf(...)` = барлығын күту, `anyOf(...)` = біріншісін күту.
- I/O тапсырмалары үшін өз executor-ыңды бер: `supplyAsync(task, executor)`.

# JVM және GC

## 26. Как работает Garbage Collector?

**Жауап.**
- GC **GC Roots**-тан (стектегі локал айнымалылар, static өрістер, белсенді ағындар, JNI сілтемелері)
  **қол жетімді емес** (unreachable) объектілерді өшіреді. Сондықтан бір-біріне сілтейтін екі объект
  (циклдік сілтеме) roots-тан қол жетімсіз болса, олар да жиналады. Бұл тәсіл **tracing** деп аталады,
  Java reference counting-ті қолданбайды.
- **Ұрпақтар гипотезасы** (generational hypothesis): объектілердің көбі жас кезінде өледі. Heap екі бөлікке бөлінеді:
  - **Young**: Eden + S0 + S1. Жиі және жылдам тазаланады (Minor GC). Мұнда аман қалған объектілердің «жасы» өседі.
  - **Old**: белгілі бір жасқа жеткен объектілер осында көшеді. Сирек, бірақ ұзақ тазаланады (Major/Full GC).
- **Алгоритм кезеңдері:** mark (белгілеу) → sweep (тазалау) → compact (жадты ықшамдау).
- **Stop-the-world** — GC кезінде қосымша ағындары тоқтап тұратын үзіліс.

| GC | Қашан таңдалады |
|---|---|
| Serial | кішкентай heap, бір ядро |
| Parallel | максимал өнімділік (throughput), үзілістер маңызды емес |
| **G1** (Java 9+ әдепкі) | теңгерімді: heap region-дарға бөлінеді, үзіліс мақсаты бар (~200ms) |
| ZGC / Shenandoah | өте үлкен heap, үзілістер < 1 ms |

⚠ `System.gc()` тек **ұсыныс**. JVM оны орындауға міндетті емес.

## 27. Бывают ли утечки памяти в Java? Какие виды ссылок?

**Жауап.** Иә, болады. GC тек **қол жетімсіз** объектілерді жинайды. Объект енді керек болмаса да,
оған әлі сілтеме бар болса, ол жиналмайды. Бұл memory leak деп аталады. Типтік себептер:
- `static` коллекция үнемі өседі, бірақ ешқашан тазаланбайды;
- тіркелген, бірақ ешқашан өшірілмеген listener-лер;
- `ThreadLocal` пулдағы ағында тазаланбай қалады;
- жабылмаған ресурстар;
- mutable кілт HashMap ішінде «жоғалып» кетеді (№1 сұрақты қара).

**Сілтеме түрлері:**

| Түрі | GC оны қашан жинайды | Қолданылуы |
|---|---|---|
| Strong | ешқашан (сілтеме бар болғанша) | кәдімгі `=` |
| Soft | жады **таусылуға** жақындағанда | кэш |
| Weak | **келесі** GC кезінде | `WeakHashMap`, метадеректер |
| Phantom | объектіні жинағаннан кейін хабарлау үшін | `Cleaner`, ресурстарды тазалау |

```java
Map<Object, String> wm = new WeakHashMap<>();
Object key = new Object(); wm.put(key, "v");
key = null; System.gc();
wm.size();   // → 0   (кілтке strong сілтеме қалмады, сондықтан жазба өшті)
```
**Leak-ты қалай іздейді:** алдымен `jcmd <pid> GC.heap_dump file.hprof` арқылы heap dump алынады,
сосын ол Eclipse MAT немесе VisualVM-мен талданады («Dominator tree», «Leak suspects»).
Heap dump-ты автоматты алу үшін JVM-ге `-XX:+HeapDumpOnOutOfMemoryError` параметрін беруге болады.

# Дерекқор және Hibernate

## 28. ACID и уровни изоляции транзакций

**ACID:**
- **A**tomicity — транзакция не толық орындалады, не мүлде орындалмайды;
- **C**onsistency — транзакция деректерді бір дұрыс күйден келесі дұрыс күйге ауыстырады;
- **I**solation — қатар жүретін транзакциялар бір-біріне кедергі келтірмейді;
- **D**urability — commit жасалған дерек құрылғы құласа да сақталады.

| Деңгей | Dirty read | Non-repeatable read | Phantom read |
|---|---|---|---|
| READ UNCOMMITTED | ✔ болады | ✔ | ✔ |
| **READ COMMITTED** (PostgreSQL, Oracle әдепкісі) | ✘ | ✔ | ✔ |
| **REPEATABLE READ** (MySQL InnoDB әдепкісі) | ✘ | ✘ | ✔ (стандарт бойынша)* |
| SERIALIZABLE | ✘ | ✘ | ✘ |

*PostgreSQL мен MySQL-де REPEATABLE READ деңгейінде phantom read іс жүзінде болмайды (MVCC арқылы).

**Аномалиялар:**
- **Dirty read** — commit жасалмаған өзгерісті оқу.
- **Non-repeatable read** — бір жолды қайта оқығанда оның **мәні** өзгеріп шығады (басқа транзакция UPDATE жасады).
- **Phantom read** — бір запросты қайта орындағанда **жаңа жолдар** пайда болады (басқа транзакция INSERT жасады).

```java
// JDBC-де изоляция деңгейін орнату
conn.setTransactionIsolation(Connection.TRANSACTION_READ_COMMITTED);
conn.setAutoCommit(false);
try { /* ... */ conn.commit(); } catch (SQLException e) { conn.rollback(); }
```
⚠ Деңгей жоғарылаған сайын қауіпсіздік артады, бірақ **өнімділік төмендейді** (көбірек құлып немесе конфликт болады).
Байланысты сұрақ: **optimistic** құлып (`@Version` өрісі, конфликт болса exception шығады) пен
**pessimistic** құлып (`SELECT ... FOR UPDATE`) айырмашылығы.

## 29. Проблема N+1 в Hibernate и как её исправить

**Жауап.** 1 запрос арқылы N ата-ана объектісі жүктеледі. Сосын әр ата-ананың LAZY коллекциясына
жүгінгенде **тағы 1 запрос** орындалады. Нәтижесінде бір запростың орнына **N + 1** запрос шығады.

```java
List<Author> authors = em.createQuery("select a from Author a", Author.class).getResultList(); // 1 запрос
for (Author a : authors) a.getBooks().size();   // әр автор үшін тағы 1 запрос → N запрос
```
**Шешімдері:**
```java
// 1) JOIN FETCH: бәрі БІР запроспен жүктеледі
em.createQuery("select distinct a from Author a join fetch a.books", Author.class);

// 2) @EntityGraph(attributePaths = "books")  — Spring Data-да
// 3) @BatchSize(size = 50) немесе hibernate.default_batch_fetch_size: коллекциялар топтап жүктеледі (IN (...))
// 4) DTO проекциясы: select new AuthorDto(a.name, b.title) from ...
```
⚠ Бірнеше коллекцияға бір уақытта `join fetch` жасау **декарттық көбейтіндіге** (cartesian product) немесе
`MultipleBagFetchException` қатесіне әкеледі.
⚠ Барлық байланысты `EAGER` етіп қою шешім **емес**: N+1 жойылмайды, тек басқа жерге ауысады.
**Анықтау тәсілдері:** SQL логтарын қосу (`hibernate.show_sql`) немесе Hibernate statistics.

## 30. Состояния сущности: Transient, Persistent (Managed), Detached, Removed

| Күй | Мағынасы | Қалай бұл күйге түседі |
|---|---|---|
| **Transient** (New) | жай Java объектісі, дерекқор оны білмейді | `new User()` |
| **Persistent / Managed** | `EntityManager` (Session) қадағалап отырады, өзгерістері commit кезінде **автоматты түрде** сақталады (dirty checking) | `persist()`, `find()`, запрос нәтижесі |
| **Detached** | дерекқорда бар, бірақ енді қадағаланбайды | `close()`, `clear()`, `detach()`, транзакция аяқталғаннан кейін |
| **Removed** | commit кезінде өшіріледі | `remove()` |

```java
User u = new User("Ali");        // Transient
em.persist(u);                   // Managed
u.setName("Aliya");              // update() шақырмасақ та, commit кезінде UPDATE орындалады (dirty checking)
em.getTransaction().commit();
em.close();                      // u енді Detached
u.setName("X");                  // дерекқорға сақталмайды
User m = em2.merge(u);           // Detached → Managed (managed болатын жаңа объект m, ал u емес!)
```
⚠ Detached объектінің LAZY коллекциясына жүгінсең, **`LazyInitializationException`** шығады.
Себебі сессия жабылып қойған.
⚠ **Entity үшін equals/hashCode:** барлық өрісті пайдаланба. Бизнес-кілтті немесе id-ны қолдан, сонда да
`id == null` жағдайын ескер. `hashCode` тұрақты болуы керек (мысалы, `getClass().hashCode()`).
